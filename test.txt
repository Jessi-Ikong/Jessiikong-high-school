The student's average = the mean of their subjects' %, so electives mean students can have different numbers of subjects. A component only counts once at least one score has been entered for it in that section; a missing score for a counted component = 0. Tied students share a position (1, 1, 3), and withdrawn students are left out. Weights don't have to add up to 100 (they're scaled).

  12. Timetable slots may have no teacher yet; that is how "unfilled slots" are represented. Each class level (JSS1, JSS2...) exists once; parallel groups are sections (A, B).
  13. ID cards get a number like JHS-000001. The QR code should use the card's random verification_token, not the card number, so strangers can't guess other cards. One active card per person per session.
  14. Deactivating a user (is_active = false) removes all their access immediately.

HOW ACCOUNTS ARE CREATED: Edge Function, not a database trigger. Here is how it works:
  1. The admin's browser calls the "invite-user" Edge Function with the form details. Supabase sends the admin's login token along automatically.
  2. The function checks the token belongs to a signed-in, active admin. If the new account is an admin, the caller must be a super admin. Otherwise it refuses with a clear message.
  3. It calls one new database function, admin_create_account(). This creates the users row and the teachers/students/parents row. For students it also creates the admission number (through the existing generate_admission_number function), the enrollment and the subject rows. All of this happens in ONE transaction: if anything is wrong (duplicate staff ID, email already used, section not in that class...), NOTHING is created and NO email is sent.
  4. Only then does it send the Supabase invite email (full_name and role go into the login's metadata), and link the new login to the users row.
  5. If the invite fails (e.g. that email already has a login), it undoes step 3 with admin_discard_account(). That also gives back the admission number, so there are no gaps.
  Why not a trigger on auth.users: a trigger would only see what's stored in the login's metadata. So class, section and subject choices would have to travel through Supabase Auth, and a mistake there would surface as a vague "error sending invite". A trigger also can't check who the calling admin is. Doing it in the function means we validate first, invite second, and report exact errors. Both new database functions can ONLY be run with the service role key: the test confirmed that even a signed-in super admin gets "permission denied" calling them from the browser.

Known issues / follow-ups:
  ASSUMPTIONS:
  1. BACKFILL: none was needed. term_id has been required on assignments since the first schema (006), so every existing row, test data included, already has the term the teacher selected when creating it. Nothing is uncertain.
  2. "7 days after the term ends" means teachers can still edit ON end_date + 7 and are locked from end_date + 8, using Nigerian time ("school today", like attendance).
  3. Both locks use the term's CURRENT end_date. If an admin later moves a term's end date, the lock moves with it, and that can reopen or close editing. That's also the simplest way for an admin to give teachers extra time.
  4. The due-date-within-term rule is only checked on the teacher page, not in the database (a soft guard, as suggested). Existing assignments aren't re-checked. Admins aren't limited by it.
  5. Only GRADING is locked. Students can still hand in (late) work for an earlier term of the CURRENT session. Such work may then arrive after the teacher's grading window, so an admin would have to grade it. If you'd rather close submissions at the same point, that's a small change.
  6. Teachers can still post or edit assignments in an older term of the current session in the database; the page just hides "+ New assignment" once a term is locked. Tell me if the database should refuse that too.
  7. Admin-graded submissions now count as graded (graded_by = the admin, graded_at set), so they lock for the student. The student sees the admin as the grader only through the audit log; the page doesn't show who graded.
  8. The pages judge "locked" by the browser's date. The database uses the school's (Nigerian) date and always has the final say. Around midnight they could differ for a moment, and the database message then explains it.
